Where ADK's root and sub-agents sit in heyrobots

ADK is the agent engine: every model turn in heyrobots runs through an ADK Runner, with ADK's agent, session, tool dispatch, model adapters and the workflow engine that runs a standing job's steps, retries and pauses. heyrobots adds the parts ADK has no concept of: a queue with capacity per agent, a Mandate that caps every agent on a task, an outbox that waits for your OK, turns that resume days later across restarts, and members that aren't ADK at all. ADK's agent tree runs inside one call of one process, so it can't hold any of that. That is why each team agent is its own ADK root, run once per piece of work, and the agents talk through stored messages, not ADK's transfer_to_agent.

1. The whole system

Every message takes the same path: code decides who may ask, a small model decides what it means, code checks that decision, and the work runs as one agent with only the tools the task was granted. Nothing reaches another person without passing the outbox.

2. The agents, and where ADK's tree fits

ADK has two shapes now: the agent tree, where a root agent lists sub-agents and can transfer the conversation to one of them inside the same run, and the graph workflow engine (ADK Go v2.7), where nodes with retries and pauses run inside one call. Both live inside one call of one process. heyrobots uses ADK for each agent's brain, and the graph for an agent's standing jobs (each job file becomes a workflow of steps, sub-jobs and "ask the owner" pauses), but builds the team above both: the router is a root agent of its own, each team agent is the root of its own run, and the task's lead agent is the root of the work. Teammates are separate runs that exchange messages stored on the task.

ADK's tree and graph still have a place: inside one agent. Its workflow agents (sequential, parallel, loop) and the graph engine split that agent's own work into steps with retries and pauses, all under the same tools and limits. That is what a standing job is. The graph can't be the team either: a busy member couldn't make work wait, a pause couldn't last days across restarts, and an ACP agent, a separate process, can't be a node in it.

4. Groups: the router is the root, not a hidden agent

A group is a scope, not an agent: a thread plus a member list. There is no coordinator model behind it. For each message the router, already an ADK root of its own, picks the lead from the members (an @Name fixes it), and that lead's task runs as its own ADK Runner, exactly like a direct chat. Members hand work to each other with stored messages; the side-talk shows in the group chat with each member's avatar. A hidden coordinator would add a model call and a prompt to cache on every message, hold everything in one session, and be one more thing that could widen a task; the router already makes that call for a few hundred tokens and plain code checks it.

6. One app, several machines, agents that talk across them

The phone app can pair with more than one heyrobots: your Mac at home, a box at the office, a hosted cell. Each stays a whole system with its own intake, router, queues, store and outbox. Nothing is shared by default. When an agent on one machine needs an agent on another, the message takes the two paths that already exist: out through the sender's outbox, in through the receiver's intake. So a cross-machine message gets the sender's reach and taint checks and your OK where its Mandate requires it, and the receiver's gate and router decide whether and who handles it, like any message from a connected app.
