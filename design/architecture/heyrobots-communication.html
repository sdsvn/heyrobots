How heyrobots talks

You talk to a team of agents that runs on your own machines. Each machine runs one server, heyrobotsd. Your devices talk to one server, the servers talk to each other, each server talks to the agents it runs and to the model providers you chose, and the agents reach your apps through it. This page explains the ideas behind those conversations and how each one works today.

The philosophy

Seven rules decide every choice below. When two of them pull apart, the earlier one wins.

You are the authority

Anything that reaches other people waits for your OK, given on your own device. Machines and agents propose; only you approve. Rules every machine shares are changed by you, never by a vote between machines.

Your machine trusts you

Whoever sits at the server's own machine is you. Its terminal prints a pairing code at every start, and the installer signs the app on that machine in by itself. Anything arriving from elsewhere has to prove itself with a code or a token.

One team, wherever it runs

An agent on the cloud, the home Mac or the office box looks and behaves the same in the app. The only visible difference is whether its machine is up: available, working, or away since a time.

Every fact has one writer

Each message, reply and decision is written once, by the machine where it happened, and never edited. Others keep copies that always end up identical. A data folder has one server too, enforced by a lock. No machine ever needs a majority to carry on.

Work happens at the agent's home

Only the machine an agent lives on runs it, holds its memory and sends what it writes. A task can never run twice, because only one machine may run it.

Fast, and never jammed

You see the agent thinking the moment you send. Steps that aren't needed are skipped. One broken app or one missing machine never stops a chat: the agent carries on without it and says what's missing.

Reach out, never in

Phones and machines only dial out. Links between machines use each machine's own key, checked both ways. Content from outside, such as an email or a web page, is treated as untrusted wherever it is read.

Five links

Everything heyrobots says travels over one of five links. Each has one job, and none of them needs to know how the others work.

1 · AppYour device and one serverMessages, chats, approvals, model choices, live updatesHTTPS with a device token from pairing. A stream of events tells the app the moment a chat changes.
2 · MachinesYour serversWho is up, each machine's agent cards, and log entries the other side is missingMutual TLS, pinned to each machine's ed25519 key. Getting connected

Installing

One command installs the server, runs it as a service that starts at login (launchd on a Mac, systemd on Linux) and installs the Mac app. It then asks the server for a one-time code with heyrobotsd pair --link and opens the app with a heyrobots://pair link. The app signs in by itself, because the link names a server on this machine. It refuses such a link for any other address, so a web page can never point the app at a server of its own.

Pairing another device

Every start prints a QR code, the addresses to open and a one-time owner code in the server's terminal or log. The QR code lists every address that works, best first: the public one if set, the tailnet one, then the network ones. The app tries them in order and keeps the first that answers. A paired device can make more codes, and heyrobotsd pair makes one at any time.

Addresses

The server always listens on 127.0.0.1, also on its tailnet address when the machine is on Tailscale, and on any network address you add. Sign-ins to your apps, such as Notion or Google, come back to 127.0.0.1, so they start from a browser or the app on the server's machine; the phone shows apps but never starts a sign-in. Listening on 0.0.0.0 is refused outside public mode.

One server per data folder

The running server holds a lock on its data folder, so a second one refuses to start instead of sharing the database. heyrobotsd status says whether one is running, and the installer uses it before starting the service.

A message's journey

What happens between pressing Send and seeing the answer. Times were measured with two servers using omp on Claude Sonnet 5.5.

  1. Stored and shown thinking. The server your device talks to stores the message once; a retry with the same id is ignored. The app shows the agent thinking at once, and keeps showing it until the reply lands.
  2. Does an open task take it? If the chat has a task still waiting on you, the message goes to that task. A finished task stays finished: in a chat, a new message is new work.
  3. Is there anything to decide? In a direct chat or with an @mention, no: the message goes straight to that agent. In a group or a new open chat, the lead picks who answers.
  4. Agreeing who decides, in shared chats only. Every machine holds a copy, so only one may route each message. The reachable machine with the newest copy claims it and routes as soon as every other machine has seen the claim. If two claims cross, every machine keeps the earliest, and the other stands down before acting.
  5. Handing over. If the chosen agent lives on another machine, a hand-off entry goes into the log, and that machine starts the task under its own rules.
  6. The work. The agent's home opens the task's tools, takes a warm agent process and sends the turn. An app that can't be reached is left out, and the agent is told to ask you to reconnect it, so the chat keeps working.
  7. The answer travels back. The reply is stored on the agent's machine, copied to the others within a second, and pushed to your app by the event stream.

The shared chat log

Machines never send each other commands. They only add entries to one log that every machine copies. Each entry carries its writer, a sequence number for that writer, and a hybrid clock: wall time plus a counter, so the order survives clocks that drift. Every machine sorts by that clock, then by writer, so all of them show the same order.

EntryWritten byWhat the others do with it
chatThe machine where a chat or group was made or changedCreate or update their copy, with the same id

routedThe machine whose lead handed work to another machine's agentThe agent's home starts the task with that agent as lead; everyone else only shows it
replyThe agent's homeShow it, signed by the agent. A copied action can't be sent or decided anywhere else
approvalThe machine your device gave the answer toThe action's home applies it, exactly as if you had tapped it there

Why there is no voting

Raft and Paxos need a majority of machines to agree before anything happens. With a laptop and a cloud server, a majority means both, so closing the laptop would stop the cloud from answering. A personal cluster is often exactly that: two machines, one of them asleep.

heyrobots needs agreement on one question only: who routes this message. Everything else has a single writer by construction. A message has one sender, a task has one home, a data folder has one server, and a setting has one authority, you. The routing question is settled by the newest-copy claim, and the worst case is visible and harmless: during a network split, two agents might each answer once, and the chat marks the second answer as a duplicate. Outward actions can never double, because only the agent's home can send them.

Shipping it

Every push runs the server's and the app's tests on GitHub. A version tag builds the server for macOS and Linux on Intel and ARM, with the web app inside, plus the macOS, Linux and Android apps, and publishes them with checksums. The installer installs the latest release. The builds aren't signed by Apple yet, which is why the Mac app is installed by the script rather than downloaded in a browser, and why it keeps its pairing in the ordinary login keychain.

Not built yet

  • Inviting another person's machines into one chat.
  • Your phone switching to another machine when the one it is paired with is down.
  • Shared rules and spending caps across machines.
  • Showing the agent's real steps, such as "Reading 3 pages", in the thinking bubble.
  • Keeping one agent session open across messages, so it doesn't re-read its instructions every turn.
  • Signing and notarizing the Mac builds, and installing with Homebrew, which needs the repository to be public.
