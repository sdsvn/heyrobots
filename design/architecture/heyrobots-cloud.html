heyrobots · a draft for a hosted version

heyrobots in the cloud

Today heyrobots is one Go binary on your Mac: one SQLite file, one vault key, agents as child processes, approvals on your phone. A hosted version keeps that shape and multiplies it. Each person gets a cell, their own copy of the server, and a thin control plane does only what a single Mac can't: stay reachable, wake cells, and relay to the devices that hold the things a cloud shouldn't.

This is a draft to argue with, not a plan that's been approved. The companion page heyrobots Agent Architecture describes what runs inside a cell.

1. The shape: cells, a control plane, and runners

The unit of deployment is the person, not the service. A cell is the unmodified heyrobotsd with its own data folder. Cells never talk to each other. The control plane owns accounts, placement, public endpoints and timers. A runner is a device the person owns (their Mac, a home server) that connects outbound and offers what it has: a subscription agent, local files, a place to run commands.

3. The technical problems

Mostly idle, never done

A task waits three days for your OK. A job sleeps until Tuesday. Keeping a process up for that is waste; killing it loses nothing only if every wait is in the store. Each cell publishes its next wake time (earliest schedule, lease expiry or retry); the control plane holds a durable timer per cell and starts the cell when it fires or when an event arrives. Intake is idempotent, so a duplicate wake is harmless.

Resume after anything

Cloud machines get preempted. Every run must survive a restart mid-task: the lease expires, the next executor picks the task up, the ACP session id in the task folder lets the agent continue its own history. Task folders have to be on a volume that follows the cell, with snapshots to object storage. SQLite on a network volume is fine for one writer; the WAL must never be shared.

Sandboxing without Docker

On the Mac, commands run in a container. In a cell, nested containers aren't available. The sandbox becomes an interface with two backends: a microVM service (one VM per task, destroyed at the end, egress allowlist) and the runner. A cloud ACP agent is itself an untrusted process with tools, so it runs inside that microVM, and the MCP bridge token is the only way back into the cell.

Secrets and the subscription problem

API keys are easy: vault plus KMS. Subscription logins are not. They are device-bound OAuth refresh tokens meant for a person's own use. Holding them server-side means storing a credential that can act as the person anywhere, and it brushes against the provider's terms. The runner avoids the problem by leaving the login where it already is.

A public edge for bots and webhooks

Each bot needs a URL that answers in seconds; Slack retries after three. Ingress verifies the provider's signature, stores the event, wakes the cell, and acknowledges. The cell then reads it through the same intake as a chat message, so it goes through Eval, the router and the Mandate like everything else.

Quarantine still applies

Outside content read in the cloud is as untrusted as on the Mac. The guard, taint tracking and the outbox stay exactly where they are. What's new is network egress: a sandbox that can reach the whole internet can exfiltrate what it read, so the microVM's egress is an allowlist built from the task's toolset.

Offline runners

The Mac is closed, so the subscription agent and local files are gone. A task that needs them ends "blocked: your Mac is offline" and resumes when the runner reconnects. The cell must say which of its tools are remote so the router can pick a cloud agent for work that doesn't need the Mac.

Cold starts and cost

A Go binary opening a SQLite file starts in well under a second, which is what makes scale-to-zero realistic. The real cost is tokens, and that ledger exists. The operator's cost is volumes and microVM minutes; both are per task, so both can be shown to the person next to the token spend.

4. Design considerations

  • The person is the cell. Don't split the server into a router service, an executor service and an outbox service. They share one Mandate, one transaction and one trace per task; splitting them turns the Mandate into a distributed check and the trace into a join. Keep the monolith and run many of them.
  • The same binary everywhere. A cell is the Mac version with a different data directory and three swapped backends: sandbox, secrets, and where files come from. Anyone can leave by copying their folder to a Mac, and the Mac version stays the reference that the cloud has to match.
  • The control plane holds nothing a person said. Accounts, placement, timers, signed events in transit. No messages, no task bodies, no keys. If it is breached, the attacker learns who uses heyrobots, not what they asked for.
  • Be honest about trust. The Mac version is trustworthy because it never leaves the Mac. A hosted cell is trustworthy only as far as the operator is. Say which secrets the operator could read, offer bring-your-own-key, and let the runner keep the most personal things home. The hybrid is a feature, not a stopgap.
  • Outbound only from devices. Runners and phones dial the relay; nothing dials into a person's network. Pairing stays a code shown on one device and typed on another.
  • Every wait has an owner. A task waits on the person, on a schedule, on a runner or on a lease, and the store says which. That is what lets a cell sleep and what the control plane's timer is built from.
  • Per-task budgets are the safety valve. The limits that exist now (calls, run time, monthly spend) are what stop a sleeping system from waking up to a surprise bill. In the cloud they also cap the operator's exposure, so they stay mandatory.

6. How to get there

Phase 1 · hybridCloud cell + Mac runner

The cell gives always-on inbox, bots, schedules and push. The Mac keeps the subscription agent, local files and commands. Code: a runner that dials the relay and serves ACP, file tools and a command sandbox over it; ACP sessions over a WebSocket instead of stdio; a wake endpoint on the cell; a sandbox backend interface.

Phase 2 · cloud-nativeCells without a runner

MicroVM sandbox, API-key models and cloud ACP agents with keys, file storage on the volume, SQLite streamed to object storage. Subscription logins stay on devices. Bring-your-own-key for the vault.

Phase 3 · leavingExport and self-host

Download the folder, run the Mac version, point the phone at it. The product promise is that this always works.

Open questions

  • Should a cloud cell ever hold a subscription login, even with the person's explicit consent, or is "subscriptions stay on your devices" the rule?
  • One cell per person, or one per household with several people inside it? The people table already has delegates; the question is who pays and who can read the store.
  • Is the runner a separate small program, or heyrobotsd itself in a "runner" mode so there is still only one binary?
  • Which sandbox first: Firecracker on our own hosts, or a hosted sandbox API that we rent per task?
